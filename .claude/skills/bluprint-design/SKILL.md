Read `readme.md` for the design rules and `HANDOFF.md` for the mapping to `apps/web`. This skill holds the design system; screen prototypes live in [bluprint-prototypes](https://github.com/BluPrint-Engineering/bluprint-prototypes), linked from their issues (ADR 0088). Production primitives are rebuilt with shadcn.

## Designing a screen

1. Read `docs/agents/issue-tracker.md`. Use a parent issue per screen for the complete spec, handoff and prototypes. Each implementation ticket is a native sub-issue with artifacts containing only its slice. Work in a scratch directory outside the repository: `README.md`, `HANDOFF.md`, `*.dc.html` and a QA prototype with frozen key states. Give each QA row `data-screen-label="{{ row.id }}"`; its state id is letters followed by a number and an optional alphanumeric suffix, such as `N3a` or `C7a2`.
2. Add missing primitives, variants and glyphs to this skill first. After changing `components/**/*.jsx`, rebuild with `bun .claude/skills/bluprint-design/build-bundle.ts`. Module-level code must not touch React: the bundle also loads before React in existing authoring tools.
3. Build with `bun .claude/skills/bluprint-design/screen-artifacts.ts build <scratch-screen-dir> [--gallery "<page>.html=<states>"]...`. It prints each page with its states, then a temporary directory. Each screen `*.dc.html` becomes `<screen>.html`; each `--gallery` becomes a page of the QA prototype with only the listed states, as ids or letter prefixes (`--gallery "qa-local.html=L*"`, `--gallery "tickets/1.33.html=C3,C3b,W4c"`), an index that jumps to each one and frames that mount as they near the viewport. Without `--gallery`, `qa.html` holds every state. Give the screen epic a gallery of its states and each implementation ticket a gallery of only its states. The directory also gets the `*.md` files, `source/` with the session's files and an `index.html`. The QA logic runs once at build time: `renderVals()` must return plain data, and a row is any object with a state `id` and a `title`; a row's `shown` and `placeholder` follow the viewport. Every page inlines the app's installed Geist fonts, pinned React/ReactDOM, the runtime, the design system and sibling screens, and runs offline; the build fails on a template that needs the network, such as an `x-import` module or a remote image. Run only trusted, reviewed prototypes. Cross-screen demo navigation is frozen; use the spec's issue links to move between screens.
4. Run `bun test ./.claude/skills/bluprint-design/screen-bundle.test.ts` after changing the builder or `support.js`. Open the built pages in a local browser and check every state: no console errors, no placeholder frames and an empty `window.BluPrintDesignSystem_d4fa62.__errors`.
5. Verify each spec claim about the current API, files and session against the code. List mismatches in the implementation PR. In a clone of `BluPrint-Engineering/bluprint-prototypes` on an up-to-date `main`, run `bun .claude/skills/bluprint-design/screen-artifacts.ts stage <temp-bundle-dir> <clone> <screen>/v<n>`: it copies the bundle into a new version folder, refreshes the indexes and commits once, refusing a folder that exists. Push that commit straight to `main`, no pull request (ADR 0088); when an agent's guard blocks the push, hand the commit to whoever can push. Then link each issue: `bun .claude/skills/bluprint-design/screen-artifacts.ts link <issue-url> <commit-sha> <screen>/v<n>/<page>.html "<name>"`. It checks the file exists at that commit, refuses a name GitHub would rewrite or a duplicate, refuses to take the issue past 10 artifacts (the issue page then hides its Artifacts section), and prints the link artifact's URL. Cite the link and the file at its commit in the issue/PR handoff.

Keep screen sources and generated bundles out of bluprint-app; only design-system changes and decisions belong in its PRs. Reading prototypes from an issue: `docs/agents/issue-tracker.md`.
