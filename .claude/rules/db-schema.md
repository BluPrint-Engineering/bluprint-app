# DB schema conventions

The designed model is `docs/data-model.md`; where it disagrees with a migration, the migration wins. Migrated so far: Better Auth's four tables plus `organization`, `member`, `license`, `project` and `project_member`. Everything below `project` in the model is designed but not migrated.

- **A table is `<name>.entity.ts` in the feature that owns it, and one line in `src/db/schema.ts`.** That barrel is the only list `createDatabase` and `drizzle-kit` read: an entity left out gets no migration and no `db.query`; `db/schema.spec.ts` fails it.
- **`src/auth/auth.entity.ts` is generated.** Change the Better Auth options in `apps/api/auth.config.ts`, run `bun run --filter @bluprint/api auth:generate`, then `db:generate` ([0013](../../docs/adr/0013-better-auth-tables-are-generated.md)).
- **`casing: "snake_case"` is declared in both `drizzle.config.ts` and `db/database.module.ts`.** In only one, the migration and the runtime query disagree on column names: it typechecks, builds, and fails on the first request. `drizzle-kit` runs in its own process and cannot import `createDatabase()`, which is why there are two.
- **Our tables never spell a column name.** `uuid("organization_id")` sets `keyAsName: false` and makes `casing` dead weight for that column. The generated `auth.entity.ts` spells them and is immune; ours are not.
- **Our ids are UUID v7 generated by Postgres** (`uuidv7()`, Postgres 18) through `uuidV7PrimaryKey()` in `src/db/columns.ts`. Downgrading Postgres breaks every migration from `0002` on, and `db:generate` never warns: the failure surfaces at `db:migrate`.
- **`license.project_id` is nullable with a unique index**: null = free, filled = consumed. The index is the real guard behind the `SKIP LOCKED` insert; keep it.
- **After pulling a migration, run it against `DATABASE_URL_TEST` too**: `drizzle-kit migrate` only reads `DATABASE_URL`.
- **When the pin tables arrive**: pin and photo ids are client-generated UUID v7 and `x`/`y` are `decimal(8,6)` normalized 0–1 ([0043](../../docs/adr/0043-client-generated-pin-ids.md)); `pin.location_id` and `pin.project_id` are denormalized on purpose, `plan` keeps a redundant `UNIQUE (id, location_id)` for the composite foreign key ([0044](../../docs/adr/0044-pin-location-denormalized-with-composite-fk.md)), and there is deliberately no unique on `plan (location_id, discipline_id)` ([0031](../../docs/adr/0031-new-plan-does-not-replace-the-old.md)).
