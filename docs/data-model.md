# Data model: draft

> **This file is not law.** The truth of the database is the Drizzle schema and the migrations. This is the **design drawn before the first migration** and, above all, **the reason for each choice**, so that six months from now nobody has to rebuild the reasoning from a `CREATE TABLE`.
>
> Expect divergence. When a migration contradicts this text, the migration wins. Fix the file in the same PR if the decision really changed; do not keep it in sync column by column.

Visual design: **[Miro board](https://miro.com/app/board/uXjVHrUOxfg=/)**. Postgres + Drizzle; provider open ([0015](adr/0015-hosting-and-providers-deferred.md)). Vocabulary: [`CONTEXT.md`](../CONTEXT.md).

---

## The spine

Everything hangs on one chain, and reading in this order answers almost every "where does this live":

```
organization → project → location → plan → pin
                          (tower, floor,
                           unit, common area)
```

Three principles the whole model serves:

1. **The effective role lives on the project membership**, never on the user ([0022](adr/0022-roles-live-on-project-membership.md)).
2. **Plans and pins hang on any `location`**, not only on units ([0030](adr/0030-plans-and-pins-hang-on-any-location.md)).
3. **The discipline is recorded on the pin**, not read from the plan it sits on ([0029](adr/0029-discipline-is-recorded-on-the-pin.md)).

## 1. Accounts, organization and license

| Table | Columns that matter | Why |
| --- | --- | --- |
| `user` | `email`, `is_platform_admin` | One account, **no global role**. The platform admin is a flag, not a membership: they belong to no organization ([0013](adr/0013-better-auth-tables-are-generated.md)). |
| `organization` | `name` | The construction company, registered by hand by the platform admin ([0020](adr/0020-organizations-are-registered-by-hand.md)). |
| `member` | `organization_id`, `user_id`, `role` | Organization membership; holds the **default role**, which only suggests and never authorizes. |
| `license` | `organization_id`, `project_id?` | Owned by the **organization** ([0019](adr/0019-license-belongs-to-the-organization.md)). `project_id` null = free; filled = consumed. Free licenses come from `WHERE project_id IS NULL`. |
| `project` | `organization_id`, `name` | Created blank by the admin from a free license. |

`session`, `account` and `verification` are generated by Better Auth's Drizzle adapter and carry no decision of ours.

Deviations from this design, settled in migration `0002` (#38); the migration wins:

- **`organization` has no `slug`.** Nothing addresses an organization by name yet, and a slug invented by self-signup scaffolding would be one more row for #12 to clean. There is no `unique` on `name` either: organizations are registered by a human, and two companies may share a name.
- **`license.project_id` arrived in migration `0003` (#39)**, together with the `project` table it references, so no column ever existed without referential integrity. It is nullable, with a foreign key and a `UNIQUE`, which is the real guard behind #40's `SKIP LOCKED` and must not be dropped as redundant.
- **Our tables use `timestamptz`** while Better Auth's generated ones use `timestamp` without time zone, on purpose ([0013](adr/0013-better-auth-tables-are-generated.md)).

## 2. Roles and invitations

| Table | Columns that matter | Why |
| --- | --- | --- |
| `project_member` | `project_id`, `user_id`, `role` | The **effective role**, the only one that authorizes. The same person can be manager on one project and assistant on another. |
| `invitation` | `organization_id`, `project_id?`, `org_role`, `project_role?`, `token`, `expires_at` | **Our** table, not the Better Auth plugin's ([0042](adr/0042-invitation-is-our-own-table.md)). |

Who may invite whom is validated in the service, not in the schema ([0023](adr/0023-invitation-hierarchy.md)).

## 3. Physical structure: the tree

`location` is one table for **tower, floor, unit and common area**, a tree by `parent_id` ([0030](adr/0030-plans-and-pins-hang-on-any-location.md)).

| Column | Role |
| --- | --- |
| `parent_id` | Parent in the tree. Null at the project root. |
| `type` | `tower` · `floor` · `unit` · `common_area` |
| `path` | Materialized ancestor chain (`/1/2/4/`). Archiving a subtree, counting per tower and building the breadcrumb become `LIKE`, not `WITH RECURSIVE`. |
| `archived_at`, `archived_by` | An item with content is never deleted, only archived ([0036](adr/0036-empty-structure-deletes-work-archives.md)). |
| `archived_directly` | `true` = archived on its own; `false` = archived in cascade. |

**Valid parent → child pairs**, validated in the service (the database alone would accept `floor` inside `floor`):

| Parent | Allowed children |
| --- | --- |
| project root | `tower`, `common_area` |
| `tower` | `floor`, `common_area` |
| `floor` | `unit`, `common_area` |
| `unit` | nothing in the tree (rooms go in `room`) |
| `common_area` | nothing in the tree (may have `room`) |

A unit **always** hangs on a floor, never directly on a tower. Common areas appear at all three levels: garage and façade at the root, party room in the tower, hall on the floor.

### `unit_detail`

1:1 with `location`, PK = `location_id`: `status`, `planned_start_date`, `is_sold`, `notes` ([0040](adr/0040-unit-detail-is-a-separate-table.md)).

Status history is **out of the MVP**. When it comes, it is a generic `activity_log` serving units and pins, not two history tables.

### `room`

Hangs on a **unit or common area**, outside the `location` tree ([0041](adr/0041-room-hangs-outside-the-location-tree.md)). Towers and floors have no rooms, so a pin on their plans has `room_id` null.

## 4. Disciplines and plans

| Table | Columns that matter | Why |
| --- | --- | --- |
| `discipline` | `name`, `color?`, `is_general`, `has_own_plan` | Applies to the whole project. `is_general` marks General, the only discipline without a color ([0028](adr/0028-general-discipline-has-no-pins.md)). `has_own_plan` false means its pins are created on the General plan. |
| `plan` | `location_id`, `discipline_id`, `storage_key`, `image_width`, `image_height` | Uploaded per location **and** per discipline. The dimensions convert a pin's normalized coordinates. |

**`UQ (project_id, color)`** already blocks blue and amber, because the plumbing and electrical seeds hold them. Gray is reserved for a completed pin and needs an application-level block ([0035](adr/0035-two-independent-palettes.md)).

**There is no unique on `plan (location_id, discipline_id)`**, deliberately ([0031](adr/0031-new-plan-does-not-replace-the-old.md)). There **is** a redundant `UQ (id, location_id)` on `plan`, required by the composite foreign key from `pin` ([0044](adr/0044-pin-location-denormalized-with-composite-fk.md)).

## 5. Pins and photos

| Column | Role |
| --- | --- |
| `id` | **UUID v7 generated on the client** ([0043](adr/0043-client-generated-pin-ids.md)). |
| `plan_id` + `location_id` | `location_id` denormalized from `plan`, locked by a composite foreign key ([0044](adr/0044-pin-location-denormalized-with-composite-fk.md)). |
| `discipline_id` | **Recorded on the pin** ([0029](adr/0029-discipline-is-recorded-on-the-pin.md)). |
| `room_id?` | The room, when the pin is in a unit or common area. Null on tower or floor plans. |
| `contractor_id?` | Starts from the unit + discipline default and can be changed on the pin without touching the default ([0027](adr/0027-contractor-default-per-unit-and-discipline.md)). |
| `x`, `y` | `decimal(8,6)`, **normalized 0–1** over the image ([0043](adr/0043-client-generated-pin-ids.md)). |
| `created_by` | Authorship. Any project member edits; only the author and the manager delete ([0032](adr/0032-editing-pins-is-collaborative-deleting-is-not.md)). |

`pin_photo` is a separate table because the MVP already targets several photos per pin; its `id` also comes from the client, for the same idempotency. Images live in S3-compatible object storage; `storage_key` holds the key.

`pin.project_id` is denormalized next to `location_id`: strictly redundant, but it is the tenancy filter of every query and index.

## 6. Contractors

| Table | Why |
| --- | --- |
| `contractor` | The project's contractors, registered in the project settings; a reusable dropdown. |
| `location_discipline_contractor` | The **default** per unit + discipline, e.g. unit 901: plumbing → Hellers, electrical → Wack. `UQ (location_id, discipline_id)`. |

There is no project-wide default, and the **absence of a row** is what the dashboard shows as "no contractor" ([0027](adr/0027-contractor-default-per-unit-and-discipline.md)).

## Still open

- **UUID v7 library in the web app.** The browser's `crypto.randomUUID()` only generates v4. A dependency choice for the pin epic.
- **The `location` table name.** Our choice; `space` and `place` were the other candidates. `location` won because the pin's field is already called "local" (place) in the product spec.
- **Rendering plans with pins** and **image handling** remain out of scope ([`ARCHITECTURE.md` §9](ARCHITECTURE.md#9-future-considerations--roadmap)).

## What deliberately does not exist

- **A report table.** Reports are generated on demand and nothing persists ([0033](adr/0033-reports-close-the-loop-on-the-device.md)).
- **Change history.** When it comes, it is a generic `activity_log`.
- **A role on `user`.** By definition: roles live on memberships ([0022](adr/0022-roles-live-on-project-membership.md)).
