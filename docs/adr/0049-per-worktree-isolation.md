# Per-worktree isolation: ports, databases and a setup script

Several git worktrees — agents or the developer — now run the app, the integration tests and E2E at the same time against the one local Postgres container. Without isolation they collide: `bun run dev` fights over 3000/5173, and `test:int`/`db:seed` truncate each other's tables. A worktree instead gets a numbered **slot** (1–9, picked as the first free one) that derives its API port (`3000+10n`), web port (`5173+10n`), E2E ports (`3100+10n`/`5273+10n`) and three databases (`bluprint_wt_<slug>`, `…_test`, `…_e2e`), written to a git-ignored `.env.local`. `apps/api`'s env loaders (`app.module.ts`'s `ConfigModule`, and the `dotenv` calls in `test/setup-env.ts`, `auth.config.ts`, `drizzle.config.ts`, `db/seed/seed.ts`) read `.env.local` before `.env`, and `process.env` still wins over both; Vite already read `.env.local`.

`scripts/worktree.ts` (`bun run worktree:setup` / `worktree:prune`, its logic in `scripts/worktree-core.ts`) automates the slot, the databases and the migrate-then-seed. The slug is the worktree's sanitized directory name plus a 6-hex hash of its absolute path, so two differently-named worktrees never collide and neither does a name that's a prefix of another's (`x` vs. `x-test`); it's recorded as `SLUG` in `.env.local` so `setup` and `prune` compute the same three database names from it instead of re-deriving or parsing them back out of a live `datname`. `setup` writes `.env.local` only after install, the shared build, the three databases, the three migrations and the seed all succeed, so a failed run leaves nothing to make the next run think it's already done. A lock file at the shared git dir (`bluprint-worktree-setup.lock`, stale after 10 minutes) is held from slot selection through that write, with an in-progress reservation per slot alongside it, so two sessions starting at once can't pick the same slot or have one's `prune` drop the other's databases before its `.env.local` exists. A `SessionStart` hook runs `worktree:setup` the first time a session opens in a linked worktree with no `.env.local`, importing only the dependency-free half of the script (`scripts/worktree-core.ts`) so it still works before `bun install` — the half that needs `pg` (installed only in `apps/api`) resolves and imports it dynamically, after install.

Secrets and flags (`BETTER_AUTH_SECRET`; `ALLOW_SELF_SIGNUP` and `API_DOCS_ENABLED`, which aren't secret but travel the same file for the same reason) stay in `.env` only, shared byte-for-byte across worktrees — `worktree:setup` copies it from the main checkout the first time, never parsing or printing it. One dev secret across worktrees is intentional: a session lives in each worktree's own database, so a cookie signed in one is simply not found in another's `session` table. The Postgres admin credentials `worktree:setup` and `worktree:prune` connect with come from the same resolved `DATABASE_URL` (process env, then `.env.local`, then `.env`) rather than a second hard-coded copy of the user/password.

`docker-compose.yml` gets a top-level `name: bluprint-app`, matching the project Docker already runs this container under (`bluprint-app-postgres-1`, volume `bluprint-app_postgres-data`). Without it, `docker compose` derives the project name from the current directory instead, and a worktree living under a different path would start a second Postgres and a second, empty volume the first time someone ran `docker compose up` from inside one — silently orphaning the real data.

## Consequences

- Cookies are not port-scoped, so one browser sending requests to two worktrees' `localhost` ports shares its cookie jar between them; testing more than one worktree by hand needs a separate browser profile per worktree.
- A worktree slot is capped at 9; a tenth concurrent worktree has no port range left and `worktree:setup` refuses.
- `worktree:prune` only ever drops `bluprint_wt_*` databases it can't match to a live worktree's `SLUG` (or one currently reserving a slot mid-setup); `bluprint`, `bluprint_test` and `bluprint_e2e` are outside its reach by construction, since it only looks at that prefix.
- Two setups can never run at once, even for different worktrees — the lock is held for the full install-through-seed duration, not just slot selection. Simpler to reason about than partial parallelism, at the cost of a queue when several worktrees bootstrap at the same moment.

## Considered Options

- Keep copying `.env.local` into a new worktree via `.worktreeinclude`, like `.env` already was: a worktree would start with another worktree's ports and database names baked in, colliding immediately instead of getting its own.
- A `BETTER_AUTH_SECRET` per worktree: no isolation benefit over one shared secret, since the database (not the secret) is what keeps sessions apart, and it multiplies what a compromised worktree checkout exposes for nothing.
- A free port found at runtime instead of a fixed slot: non-deterministic, so a worktree's URL can't be bookmarked or relied on between sessions, and it stops lining up with the fixed `E2E_API_PORT`/`E2E_WEB_PORT` pair CI needs to know in advance.
- A schema per worktree instead of a database per worktree: Postgres, Drizzle and Better Auth all assume `public` by default in places, so every query, migration and the seed's `TRUNCATE` would need schema-qualifying by hand; a database is the isolation boundary Postgres already gives for free.
- Setup by hand instead of a `SessionStart` hook: the point of a slot and three databases per worktree is to remove a step a parallel agent can forget; a manual `bun run worktree:setup` reintroduces exactly that failure mode.
- One Postgres container per worktree (`docker compose -p`): sidesteps the shared-container database naming entirely, but multiplies running containers and leaves the port collision on `bun run dev` unsolved anyway.
- A fixed port offset per developer instead of per worktree: doesn't help the actual problem, which is several worktrees on the *same machine*.
